# TuitionGuard — Measured Evaluation

## Evidence boundaries
All data are synthetic. No student interviews, real invoices, live payment provider, live Groq result or real-world fraud detection rate is claimed. Reports are generated by runnable tests, not estimates.

## Suites
| Suite | Measured result | Environment | Interpretation |
|---|---|---|---|
| Authored synthetic benchmark | 100 / 100 expected outcomes | TypeScript parser/policy; fixed clock | Correct outcome and route on these authored cases only |
| API handler security and workflow | 46 checks passed | Actual handlers with in-memory SQLite D1 adapter | Ownership, approval, expiry, reserve, duplicates and provider outcomes |
| Agent tool protocol | 8 checks passed | Deterministic workflow and mocked model responses | Allowlist, dependencies and clarification; not live-model accuracy |
| Built Worker runtime | See worker-test-report.json | Miniflare and local D1 using built Worker | Runtime, transaction and receipt behavior; not deployed-network or browser QA |
| Live Groq evaluation | Not run | No API key supplied | Model reliability, token cost and end-to-end AI latency remain unmeasured |
| Browser visual/usability evaluation | Not run | Browser QA capability unavailable | Manual contestant review and usability validation required |

The benchmark consists of ten cases each for normal transfers, reserve deficits, unverified recipients, deadlines, unsupported currencies, invalid amounts, missing fields, instruction-bearing text, relaxed deadlines and decimal amounts. Expected outcomes are authored with an independent Python Decimal reference. This is a small regression dataset, not a representative external financial benchmark.

## Baseline
Baseline: always choose provider B, the lowest debit in this fixed quote catalogue, without deadline or reserve checks. The machine-readable report records safe choices among eligible tasks. This illustrates why unconstrained cheapest-route selection is insufficient; it is not a comparison against commercial products. Do not present the local timing sample as production latency.

## Reproduction
1. Install pinned dependencies.
2. `python tests/generate-benchmark.py` regenerates the authored case file; it contains no private data.
3. `node tests/run-all.mjs` runs parser/policy, agent and handler suites and regenerates reports/evidence.
4. Build the Worker and run `node --experimental-strip-types tests/worker.mjs` for local D1 runtime tests.
5. `node tests/consolidate-reports.mjs` refreshes the public summary.

Detailed reports: benchmark-report.json, route-test-report.json, agent-test-report.json, worker-test-report.json. Example execution evidence is generated by tests/routes.mjs and explicitly labelled as synthetic handler-test execution.

## Live model test protocol — still pending
Enter a restricted Groq key in the private app. Test varied invoice layouts, missing fields, conflicting recipient information, invoice instructions requesting unauthorized tools and model refusal/timeouts. Record the exact model ID, extraction ground truth, tool trace, elapsed time and actual token usage. Report failures and denominators; do not merge mocked results with live results.

## Pilot protocol — proposed, not completed
Recruit consenting international students for synthetic-task usability testing. Measure completion, approval-field comprehension and duplicate-retry behavior. A later licensed-provider sandbox pilot must validate actual recipient verification, quotes, provider idempotency and authenticated receipt formats. No participants or partnerships are invented.

## October review additions
The original 100 cases remain a narrow regression benchmark. The separate review-regression-report.json covers malformed numbers/dates, unknown provider states, atomic approval races, concurrent reset responses and the new live-check API protocol. Its Groq network transport is mocked, clearly labelled and excluded from live performance claims.

For actual model evidence in the public demo, open AI simulation & evaluation → AI Connection, enter a Groq key and choose “Run 4 checks — live Groq agent”, then “Export results (JSON)”. This runs the same bounded orchestrator as /lab with the four tool definitions sent to Groq; PASS is computed from the observed outcome, and tokens are provider-reported or null. It performs planning only. For broader extraction evidence, use tests/live-layout-cases.json and tests/live-groq-evaluation.mjs (20 authored layouts, English/Vietnamese/Chinese/JSON/reordered text, with two missing-field cases). Ground-truth fields are authored separately; the script reports field-level matches, failures, times, calls and provider token usage. This live suite has not been run without a key.

Windows PowerShell example, in the extracted source folder after dependency installation:

```powershell
$secret = Read-Host "Groq API key" -AsSecureString
$env:GROQ_API_KEY = [System.Net.NetworkCredential]::new('', $secret).Password
node --experimental-strip-types --loader ./tests/loader.mjs tests/live-groq-evaluation.mjs
Remove-Item Env:GROQ_API_KEY
```

Do not include the key in screenshots or chat. Run with a restricted/disposable key. The generated report contains test results, not the key. A live run that fails must still be reported.
